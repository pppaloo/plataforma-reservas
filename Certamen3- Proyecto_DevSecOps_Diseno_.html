1. Contexto del certamen

Una empresa u organización requiere implementar una plataforma web para presentar sus servicios, interactuar con clientes y administrar información mediante un sistema centralizado. La solución deberá ofrecer una experiencia funcional y segura, contar con autenticación de usuarios, un panel administrativo, una base de datos NoSQL y canales digitales de comunicación.

El equipo de desarrollo deberá construir la solución, publicarla en un hosting accesible desde Internet y aplicar prácticas de DevOps y DevSecOps durante el ciclo de vida del software. La aplicación publicada deberá ser sometida a pruebas de seguridad; las vulnerabilidades identificadas deberán analizarse, corregirse y verificarse mediante un nuevo escaneo.

Desafío: no basta con desarrollar una página visualmente atractiva. Se deberá demostrar que la plataforma funciona, protege la información, puede desplegarse de manera controlada y permite detectar y corregir debilidades de seguridad.

Objetivo general

Diseñar, desarrollar, desplegar y securizar una plataforma web utilizando Node.js y una base de datos NoSQL, incorporando autenticación JWT, protección de credenciales, administración de usuarios, comunicación con clientes, automatización DevOps y análisis de vulnerabilidades mediante prácticas DevSecOps.

Fecha y modalidad de entrega

Fecha límite: jueves 12 de noviembre de 2026. El proyecto completo deberá ser adjuntado en la plataforma EVA, dentro de la actividad habilitada para este certamen.

La entrega deberá identificar a todos los integrantes del equipo. Se deberá incluir el nombre completo de cada integrante en la información de entrega y en un archivo README o documento de presentación incorporado al proyecto.

El envío deberá contener el enlace al repositorio GitHub, la URL pública de la plataforma desplegada y los documentos e informes solicitados en este certamen. Es responsabilidad del equipo verificar que los archivos queden correctamente cargados y que la entrega sea visible en EVA.

2. Alcance y definición del caso

Cada estudiante o equipo deberá seleccionar una organización ficticia o real (con autorización para utilizar su identidad) y definir el problema o necesidad que resolverá la plataforma.

Se sugieren los siguientes contextos:

  • Sistema de reservas y atención de clientes.
  • Portal de servicios profesionales.
  • Tienda de comercio electrónico.
  • Plataforma de gestión académica.
  • Sistema de inventario y solicitudes.
  • Portal de administración de servicios para una organización.

La solución deberá incluir una descripción del problema, público objetivo, funcionalidades principales y alcance. No se aceptará una página estática como solución completa.

4. Autenticación, autorización y protección de credenciales

4.1. Autenticación JWT

Se deberá implementar un mecanismo de autenticación basado en JSON Web Tokens (JWT) que considere, como mínimo:

  1. Registro de usuarios.
  2. Inicio y cierre de sesión.
  3. Generación y validación de tokens JWT.
  4. Protección de rutas y endpoints privados.
  5. Expiración de tokens y estrategia segura de renovación o reautenticación.
  6. Control de acceso basado en roles.
  7. Respuestas adecuadas ante tokens ausentes, inválidos o expirados.
RolPermisos mínimos
AdministradorGestionar usuarios, roles, contenidos, solicitudes y configuración de los módulos administrativos.
Usuario registradoAcceder a las funciones habilitadas para su perfil y administrar sus propios datos cuando corresponda.
VisitanteConsultar información pública, utilizar el formulario de contacto y acceder al chatbot.

4.2. Hash de contraseñas

Las contraseñas deberán almacenarse utilizando bcrypt o Argon2. Se exige:

  • Generar el hash antes de guardar la contraseña.
  • Verificar contraseñas mediante las funciones de comparación correspondientes.
  • No almacenar ni devolver contraseñas en texto plano.
  • Excluir hashes y datos sensibles de las respuestas de la API.
  • Gestionar los secretos mediante variables de entorno.
Importante: JWT no cifra los datos de su contenido. No se deberán incluir contraseñas, secretos ni información sensible en el payload del token.

5. Administración de base de datos NoSQL

La solución deberá utilizar una base de datos NoSQL y contar con un mecanismo de administración documentado. Se recomienda MongoDB Atlas.

Requerimientos mínimos:

  1. Crear una base de datos y sus colecciones.
  2. Diseñar documentos y relaciones de referencia o embebidas de acuerdo con el caso.
  3. Configurar un usuario de base de datos para la aplicación con privilegios mínimos.
  4. Separar las credenciales de base de datos del código fuente.
  5. Implementar validaciones de estructura e integridad.
  6. Crear índices cuando sean necesarios.
  7. Documentar el procedimiento de respaldo y recuperación o exportación.
  8. Demostrar la administración y consulta de los datos.
Principio de mínimo privilegio: la aplicación no deberá conectarse utilizando una cuenta con permisos globales de administración. Se deberá utilizar una cuenta específica con los permisos estrictamente necesarios.

6. Formulario de contacto, correo electrónico y redes sociales

6.1. Formulario de contacto Obligatorio

La plataforma deberá incluir un formulario que permita a los visitantes enviar consultas o solicitudes a la organización.

CampoCondición
NombreObligatorio.
Correo electrónicoObligatorio y validado.
TeléfonoOpcional.
AsuntoObligatorio.
MensajeObligatorio, con límites de longitud.

6.2. Flujo de envío de correo

  1. El visitante completa y envía el formulario.
  2. El frontend valida los campos y el backend vuelve a validar la información.
  3. El backend registra la solicitud en MongoDB.
  4. Se envía un correo al buzón institucional configurado.
  5. Se envía una confirmación al correo proporcionado por el cliente.
  6. La interfaz informa el resultado del envío sin revelar datos internos.
Recomendación técnica: utilizar Nodemailer con SMTP o un proveedor de correo transaccional. Los dos mensajes deberán generarse desde el backend. El destinatario institucional debe estar definido en la configuración del servidor y nunca ser controlado libremente por el visitante.

Seguridad del formulario y correo

  • Validar y normalizar los datos recibidos.
  • Prevenir inyección de encabezados de correo.
  • Implementar rate limiting y protección antispam.
  • Considerar CAPTCHA o mecanismo equivalente.
  • Guardar credenciales SMTP en variables de entorno.
  • No incluir secretos ni información sensible en los logs.

6.3. Integración de redes sociales Obligatorio

La plataforma deberá mostrar enlaces a los perfiles oficiales de la organización. Se podrán incorporar Instagram, Facebook, LinkedIn, TikTok y WhatsApp Business, según el contexto del proyecto.

El panel administrativo deberá permitir agregar, editar, activar y desactivar enlaces sin modificar el código fuente. Los enlaces externos deberán validarse y abrirse con medidas de seguridad apropiadas.

7. Chatbot de atención al cliente

Se deberá implementar un chatbot accesible desde la plataforma, mediante un botón o ventana flotante, para orientar a los visitantes y responder consultas frecuentes.

Funcionalidades mínimas

  • Mensaje automático de bienvenida.
  • Interfaz para enviar y recibir mensajes.
  • Menú de opciones o categorías de consultas.
  • Respuestas a preguntas frecuentes.
  • Opción para solicitar contacto con un ejecutivo.
  • Registro de preguntas y respuestas o conversaciones en MongoDB, cuando corresponda.
  • Mensaje alternativo cuando no exista una respuesta disponible.

Implementación

El chatbot mínimo deberá funcionar mediante reglas o preguntas y respuestas administrables desde MongoDB. Se valorará que el administrador pueda crear, editar, activar y desactivar respuestas sin modificar el código.

La integración con un servicio de inteligencia artificial será opcional y podrá considerarse como funcionalidad avanzada, siempre que se protejan las claves de API y se controle el acceso a información privada.

Seguridad: validar entradas, limitar frecuencia y tamaño de mensajes, evitar que el chatbot revele información privada y no permitir que ejecute acciones administrativas sin autenticación y autorización.

9. DevSecOps: análisis de vulnerabilidades y correcciones

La seguridad deberá incorporarse durante el desarrollo y antes de la entrega. Cada equipo deberá realizar análisis de código, dependencias y comportamiento de la aplicación desplegada.

9.1. Herramientas sugeridas

HerramientaTipo de análisis / finalidad
OWASP ZAPDAST: análisis dinámico de la aplicación web.
GitHub CodeQLSAST: análisis estático de código compatible.
npm auditIdentificación de vulnerabilidades conocidas en dependencias Node.js.
SnykAnálisis de dependencias y riesgos de componentes, como alternativa o complemento.

9.2. Riesgos mínimos que deberán evaluar

RiesgoVerificación esperada
Control de acceso deficienteComprobar que un usuario no pueda acceder a recursos o funciones de otro rol.
Autenticación débilEvaluar controles de acceso, sesiones, expiración y validación de tokens.
InyecciónEvaluar entradas que puedan alterar consultas o procesamiento de datos.
XSSComprobar que entradas y contenidos no permitan ejecutar scripts no autorizados.
Configuración inseguraRevisar HTTPS, cabeceras, CORS, mensajes de error y configuración del servidor.
Exposición de datosVerificar que no se filtren credenciales, datos personales, hashes o secretos.
Dependencias vulnerablesAnalizar paquetes y versiones utilizadas por el proyecto.
Protección insuficiente de formulariosEvaluar spam, validaciones, límites de envío y manipulación de entradas.

Se utilizará como referencia el OWASP Top 10 vigente o la versión indicada por el docente.

9.3. Corrección y verificación

Por cada hallazgo relevante, el equipo deberá:

  1. Registrar la vulnerabilidad y la herramienta que la detectó.
  2. Indicar evidencia, componente afectado y nivel de riesgo.
  3. Explicar el impacto potencial.
  4. Proponer y aplicar una corrección técnica.
  5. Ejecutar nuevamente el análisis.
  6. Comparar los resultados antes y después.
Evidencia obligatoria: informe comparativo con hallazgos iniciales, correcciones aplicadas y resultado de la verificación posterior. No se otorgará el puntaje completo por presentar únicamente capturas del escaneo sin análisis ni correcciones.

9.4. Integración de seguridad en CI/CD

Se deberá incorporar al menos una validación de seguridad automatizada en el pipeline. Se valorará que el flujo detenga o marque como fallido el proceso ante pruebas fallidas o vulnerabilidades que superen el umbral de severidad definido por el equipo y justificado en la documentación.

12. Defensa técnica y demostración

Durante la presentación, el docente podrá solicitar que el equipo demuestre los siguientes escenarios:

  1. Registrar un usuario y comprobar que la contraseña no se almacena en texto plano.
  2. Iniciar sesión y explicar la generación y validación del JWT.
  3. Intentar acceder a una ruta protegida sin token.
  4. Intentar acceder al panel administrativo con un usuario sin permisos.
  5. Mostrar la estructura y administración de la base de datos.
  6. Enviar el formulario y comprobar el registro, el correo institucional y la copia al cliente.
  7. Modificar un enlace de red social desde el panel administrativo.
  8. Interactuar con el chatbot y demostrar la gestión de preguntas y respuestas.
  9. Mostrar el repositorio y ejecutar o revisar el pipeline CI/CD.
  10. Presentar el resultado del análisis de vulnerabilidades.
  11. Explicar una vulnerabilidad detectada, su impacto y la solución aplicada.
  12. Ejecutar o mostrar el análisis posterior a la corrección.
La defensa forma parte de la evaluación. Cada integrante deberá conocer la arquitectura, el código y las decisiones de seguridad implementadas. No será suficiente presentar funcionalidades que el equipo no pueda explicar.

14. Condiciones y restricciones

  • Los escaneos y pruebas de seguridad deberán realizarse exclusivamente sobre la aplicación propia o infraestructura para la cual exista autorización explícita.
  • No se permitirá realizar pruebas contra sistemas o servicios de terceros.
  • No se deberán publicar claves, contraseñas, tokens ni credenciales en repositorios o documentación pública.
  • Las pruebas deberán ejecutarse en un ambiente controlado y con respaldo de información cuando corresponda.
  • Los estudiantes deberán documentar las herramientas utilizadas y los resultados obtenidos.
  • No se aceptará ocultar un hallazgo eliminando una funcionalidad sin una justificación técnica válida.
  • La aplicación deberá permanecer operativa y disponible para su revisión en la fecha de evaluación.
  • El equipo deberá respetar las condiciones de uso de los proveedores de hosting, correo y base de datos seleccionados.
Criterio transversal: una plataforma visualmente atractiva que no implemente correctamente los controles de seguridad, o que no pueda demostrar su funcionamiento, no podrá obtener el puntaje completo de los criterios asociados.

Resultado esperado

Al finalizar el certamen, cada equipo deberá entregar una plataforma empresarial funcional, desplegada y accesible mediante HTTPS, con autenticación y autorización, base de datos NoSQL administrada, panel administrativo, formulario de contacto con envío de correos, integración de redes sociales, chatbot y un proceso demostrable de DevOps y DevSecOps.

El propósito central es que los estudiantes demuestren que pueden construir una solución web, operarla en un entorno real y evaluar críticamente su seguridad, identificando y corrigiendo vulnerabilidades durante el ciclo de vida del software.
